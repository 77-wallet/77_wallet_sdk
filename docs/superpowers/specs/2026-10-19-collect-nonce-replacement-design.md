# 归集同 nonce 替换与恢复设计

状态：2026-10-19 用户已明确批准仅当前测试地址实施；代码及离线验证进行中。基线：SDK `442b4a194a69df0fb5faaa3dfceacca34a526ca0`。

## 已确认目标及边界

来源：2026-10-19 当前会话，用户明确选择用新的归集业务交易替换旧 nonce=6，要求一起完成替换关联、结果对账和本地153计数器恢复。本轮允许代码修改和离线验证，禁止真实签名、广播及运行数据库修改；不含提交、推送或插件发布。源码中不得硬编码本次地址、订单号、6或153。

成功标准：真实业务新单能竞争旧单所占 nonce；原始签名不丢失；进程重启能恢复关联和竞争结果；只确认实际上链的交易所属订单；已消耗 nonce 后能继续分配，不被旧高水位卡住。旧单胜出不能触发新单再次转账。

本次只扩展 EVM 归集替换。手续费、提币仍使用公共 nonce 占用与恢复结果，但不能把任意失败订单当作可替换订单。普通新单构建失败仍不占号。

## 代码事实和能力复用

- `ApiCollectRepo::reserve_signed_collect` 已在 SQLite 写事务中重验 nonce 与生命周期并保存签名事实；沿用该提交边界。
- `ApiNonceDao::signed_nonce_decision` 已跨归集、手续费、提币读取签名占用；现有失败签名保护不能删除。
- `ApiCollectRepo::fail_verified_nonce_gap` 仅报业务失败，保留原始交易；这不构成链上取消。
- `Tx::finalized_nonce_conflict`/`eth_nonce_conflict` 有独立已确认冲突核对能力，但当前仓储仅接收 eth/bnb，Scroll 不能直接复用该落库入口；扩展时必须验证 Scroll RPC 对历史状态、finalized 的真实支持，失败保留不确定状态。
- `EthTx::build_fee_setting`/`build_transfer_raw` 负责 EIP-1559 费用和最终余额检查；替换费率应在同一适配器内设置，不另建签名器。
- 原 `TxExecReceipt` 根据当前订单事实决定成功/失败，不能用旧 hash 冒充新单成功。
- 运行时观测：本地址当时 chain next6，本地高水位153，旧6已报失败；当前新单未签名。这些是时间相关诊断事实，不作为通用规则。

## 选定方案

复用现有构建、广播、恢复和回执流程，补一个数据库内的替换关联记录及可验证的 nonce 恢复检查点。没有独立取消交易，没有手工改库或无条件重置计数器。

### 关联及状态

新增 API transaction 库 migration，持久化一组替换关系，至少记录：

- chain、规范化 sender、nonce；旧/新 trade_no；旧 hash 和不可变原始签名摘要；新 hash；创建/更新时间。
- `prepared`、`signed`、`resolved` 状态及 `winner_hash`、执行成功/失败、区块号/hash、确认依据。
- 准备时的旧计数器、恢复检查点和验证依据。

旧 raw/hash 继续保存在旧订单中，不覆盖。新 raw/hash 只属于新订单。关系不是“已取消”证明。每个旧签名槽同一时刻仅一个活动替换；一个新订单只能属于一个关系。数据库唯一约束而非仅内存锁保障这一点。

关系准备可以持久化，但不能因此认为新签名已存在。构建失败/超时/取消不消耗新号，不清除旧签名；同一新单可以恢复准备态后重试。已签名后只重播相同 raw，不重复创建不同费用签名来扩大竞争集合。需要进一步加价时必须作为可审计的下一次替换尝试记录，不能覆盖当前签名。

### 准备及提交

1. 独立读取链 nonce 和双方链上结果。RPC 错误、`null` 或 pending 数字不是旧签名作废的证明。
2. 仅当旧单是已上报跳号失败的 EVM 归集、旧签名仍存在、新单尚未签名且生命周期允许构建时，考虑替换。
3. 旧/新链、sender 必须一致；币种/代币及执行目标必须符合当前业务归集授权。未经授权的跨币种或地址更换拒绝替换。旧单关联多义、同槽有未知第三方签名或已有其他活动替换时不得猜测选一个。
4. SQLite 写事务内准备关系；读取原始旧 hash、nonce 和高水位作为预期条件。并发新单只有一个能取得关系。
5. 新单保留原业务金额、摘要及收款地址校验，使用相同 nonce，并按新余额和替换后的实际费用检查资金。
6. 原子提交新签名、关系新 hash 和 nonce 占用。重验旧签名、关系拥有者、新单生命周期和链观测，任何冲突全部回滚。构建发生链外竞态时不把占号保护永久解除。
7. 广播前再次查询竞争结果；已知旧交易上链时停止新交易广播并对账。查询与广播间无法消除竞争，最终以链上结果处理。

### 费用

从旧已签名 EVM envelope 解析 chain_id、sender、nonce、maxFeePerGas 和 maxPriorityFeePerGas（兼容支持范围内 legacy gasPrice）。验证签名 hash/身份与旧订单一致，不使用总手续费反推费率。

通过当前适配器报价与替换下限计算新费用；两项 EIP-1559 费率都必须满足节点要求并留整数上取整余量，不能只提高总手续费或 gasLimit。当前 Scroll 节点具体替换门槛在实现阶段用官方源码/文档核实；门槛不可核实时使用保守的可解释加价，并将 underpriced 识别为需重新报价的明确状态，而不是永久重试同一失败候选。

保留 Scroll L1 数据费及签名最大成本余额检查。新订单给定金额不足以同时支付替换费用时，按现有余额/费用失败流程报告，不擅自减少金额、不自动补款。离线测试使用生成的测试密钥，禁止接触设备真实私钥。

### 竞争结果对账

| 链上已核实结果 | 本地处理 | 回执处理 |
| --- | --- | --- |
| 新 hash 执行成功 | 新单正常成功；关系赢家为新 hash；旧签名标记已被竞争交易消耗 | 新单沿用正常成功回执；旧单已报失败历史不覆盖 |
| 新 hash 执行失败 | nonce 仍已消耗；新单失败；关系记录新 hash 的失败结果 | 上报新单链上失败 |
| 旧 hash 执行成功 | 记录旧 hash 实际成功、关系赢家为旧 hash；禁止新单再次执行 | 新单报告替换未胜出并附旧 hash/nonce/实际结果；不能把旧 hash 作为新单成功 |
| 旧 hash 执行失败 | 记录旧 hash 实际失败和 nonce 消耗；新单不再使用该槽 | 新单报告替换未胜出；下一笔需按新余额重新下发 |
| 确认被第三笔交易消耗 | 保存冲突证据，停止本对替换尝试 | 新单报告真实 nonce 冲突，不冒认赢家 |
| 仍 pending、双方查不到、查询失败或证据不一致 | 保留关系和签名，持久化等待原因、退避后重查 | 不虚报链上成功，不自动重新签名/补号 |

对账证据必须验证 sender、chain、nonce、hash、回执区块一致及规范链确认；复用既有深度/确认策略。节点不支持所需查询时持久化可诊断状态，不能依据 `latest > nonce` 单独猜赢家。

赢家和 loser 终态更新在一个写事务完成；预期旧/新 hash 都参与条件更新。重复或乱序观察不翻转已确认赢家。区块重组导致证据失效时进入需重新核实的状态，不能复用签名槽进行第二次转账。

旧单已上传的失败回执不能假定后端支持覆盖成功。先保留该历史，再在替换记录中保存实际旧交易结果，并通过新单的失败说明引用。若产品要求后端修改旧单最终业务状态，需要核对现有接口的幂等/状态变更契约后另行确定；当前设计不承诺通过重复上传旧单成功回执实现覆盖。

### 153 高水位恢复

保留历史计数器作为审计事实。只有关联交易已核实消耗该 nonce，且跨归集/手续费/提币的签名占用已完整重读时，才发布恢复检查点。

检查点记录：地址/链、已消耗 nonce、赢家/区块证据、当时旧计数器、恢复前沿及当前所有高位签名所有权。分配器基于链前沿和仍有效签名记录计算候选，不能继续把已证明仅为历史预占的高水位当作下一个号。

- 新/旧6消耗后，chain next7且7以上无有效签名，还必须核实旧计数器覆盖区间的性质，不能仅凭三表无记录断言7～153未签过。
- 可证明历史未签预占：分配审计/构建失败记录足够完整，且恢复前已停止旧写入者、等待当前构建完成并建立地址级持久化恢复屏障。恢复检查点记录证据摘要和写入世代，所有分配/签名提交入口事务重验世代；旧写入者不能继续发布候选。证据不足时不走此路径。
- 当前测试事故的备选路径（尚未授权）：用户明确允许仅针对该测试地址，把无签名对应的指定历史区间视作无效预占，接受未知旧签名可能出现的风险。经上述停写/世代隔离后，保存授权范围与旧153审计记录，再发布有效分配前沿7；不能把该授权泛化到其他地址或生产，也不在App启动时自动启用。
- 两种依据都不存在时，替换结果仍正常对账，但153恢复保持明确的待核实状态，不承诺自动分配7。
- 有高位签名时继续保护其槽位；存在未知保留或不完整证据时等待并报告明确原因。
- 旧版本写入或其他进程产生超出检查点范围的新预占时，检查点失效，必须重新核对。
- 检查点和有效签名对账在同一事务发布，不能先降低计数器再补证据；签名提交需事务重验检查点，防止并发重复分配。
- 通用手续费/提币不能借该检查点绕过自身签名保护。

## 恢复、并发及报告

重启后通过现有 scanner 找到活动关系并恢复：准备态重新核对，签名态查询双方，已解决态完成尚未完成的原回执上传。后端上传失败不能回滚链上对账结果；回执重试不能重新转账。替换失败不可用“清 raw 重建”路径悄悄移到下一 nonce。

状态必须能区分等待链结果、等待后端回执、费用不足、费率低于替换要求、未知第三方占用、恢复证据不足，不再让确定性的错误只清 build slot 后无限重复。

## 验证与实现范围

预计涉及 wallet-database 和 wallet-api；先数据库后适配器再 worker/scanner，各批保持一个模块/流程，逐批小范围验证。已有工作区其他未提交改动不混入。

必要回归：

- migration 首次安装/升级；唯一关系约束、事务回滚、并发两个新单争抢旧6。
- signed6/counter153 的替换准备与真实候选保存；失败不额外占号；重启重开库后关联仍在。
- 费用两项加价、整数溢出、原始 hash/nonce/chain 不匹配、最大费用及L1费不足。
- 新赢家成功/失败、旧赢家成功/失败、第三方冲突、RPC错误/空值/乱序/重复回执。
- 后端失败回执重试及旧失败历史保留；不能将旧 hash 上传为新单成功。
- 已消耗6后分配7，不跳153；高位有效签名、新的未知保留、跨归集/手续费/提币并发不复用。
- 正常不替换归集的成功、失败、构建超时/取消、广播不确定行为保持。

证据为临时SQLite、模拟后端/链边界及离线测试密钥。真实链/后端、设备运行库及签名广播不在本轮验证范围。实现后固定HEAD、完整diff、源文件指纹和实际检查结果，发起独立只读审查；审后变化补审。

## 设计确认点

本设计中，旧6先胜出时：新单失败并附实际旧结果，不自动再转；旧单已报失败历史保留，实际结果另记关联账。不假定后端可覆盖旧回执。153历史区间目前缺少完整的未签证据。需要用户选择先补齐可核验证据，或明确允许仅当前测试地址使用上述限定恢复路径并接受残余未知签名风险。确认此书面设计及这一边界后，再进入详细实施计划及代码阶段。

## 本轮实际启用边界

默认关闭，通过 dev 且非 prod 配置 `collect_replacement_recovery` 精确匹配 sender、旧订单/hash、nonce 和遗留计数器上限。未修改运行配置或设备数据库。关系建立后持久化授权以支持重启恢复；移除配置不会抹掉已签名关系或停止其对账。

本轮只支持 Scroll 原生币、同 sender/收款地址/资产的新归集单。新签名前验证旧签名 hash、chain id、nonce、sender；费用下限为旧 max fee 与 priority fee 各自的 125% 加 1 wei，最终仍由既有余额和费用检查决定是否可构建。

只在交易 receipt、交易本身、canonical 区块和 finalized 高度一致后落库赢家。实际费用取 canonical receipt 的 gasUsed × effectiveGasPrice + Scroll l1Fee，资源消耗取 gasUsed；缺少实际费用字段则继续等待。新单成功以实际费用落库；旧单胜出或任何赢家执行失败，新单上报失败。旧订单原失败回执保持历史事实，真实链上赢家另存关系，不伪造新单成功。已上报失败的新签名仍扫描链上结果，其后迟到成功只记真实赢家，不自动翻转已上报业务结果。

153 保留为审计高水位。确认该槽已消耗后，公共分配器忽略范围内已核验的遗留计数器，仍检查归集、手续费、提币的真实签名占用；没有更高占用时下一笔为 7。超过授权上限的未知计数器继续阻塞。数据库保护仅在赢家未确认时阻止旧的先占计数器路径制造新虚占；确认后恢复当前签名事务正常对齐独立查询的链前沿。

finalized 证据暂不可用、RPC 超时、未知赢家时保留等待，不承诺立即恢复。离线验证不证明实际 RPC 接受替换费率，也不包含真实签名、广播、手机构建或部署。

低价拒绝边界：收到 underpriced 后持久化 `replacement_requires_requote` 业务失败，现有回执通道上报，保留两份签名并继续观察。当前授权仅这一笔替换，不自动二次加价重签；再次替换需保留完整签名集合的另一次审计尝试，不能直接覆盖本关系。

激活参数准备在 `target/collect-replacement/approved-scope.yaml`，未安装到运行 App。实际发布时需将同名顶层字段合入 dev 配置；用户当前禁止真实签名广播，故本轮不激活、不启动运行路径。
