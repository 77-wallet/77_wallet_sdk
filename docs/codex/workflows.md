# Workflows

## Low-Token Task Input Template

每次发给 Codex 的任务输入建议固定 5 段：

1. 目标（1-2句）
2. 改动边界（允许改哪些文件 / 禁止改哪些文件）
3. 必跑命令（精确到 crate/test target）
4. 输出要求（变更清单 + 关键断言 + 命令结果摘要）
5. 文档同步要求（matrix/checklist/plans 是否更新）

建议追加约束语句：

- 只跑受影响测试，不跑全量
- 不要长解释，只给结论和证据
- 新规则优先写到 `docs/codex`，不扩展 root `AGENTS.md`

## Execution Workflow

执行时遵循以下硬限制：

- 一次只处理一个模块、一个 flow
- 一次最多 3 个可执行子任务
- 只跑受影响测试目标，不跑全量

### Step 1 — Scope

- 确认任务目标与边界：开发前列出允许改变行为的入口、必须保持旧行为的入口及其关键契约（如金额/余额校验、返回错误与副作用）；按风险选取关键不变用例，记录在现有任务说明或 `PLANS.md` 中。普通小改简要列明即可，不要求全组合矩阵。
- 先读适用的 [已确认项目背景](architecture.md#confirmed-project-context)，再查代码、配置和现有文档能确认的事实及可复用能力，避免重复体系。
- 识别影响方案的业务规模、支持场景与兼容要求；设计迁移或兼容方案前，优先从明确需求、实际使用阶段及已有确认核实是否须保留旧数据库、支持既有数据或接口。确实未知且影响方案时才询问用户，只问当前关键缺口；已有事实只核实变化，不重复确认。单次任务接受卸载重装等决定仅适用于已确认范围，不能泛化为其他项目或任务无需兼容。
- 用户补充的可复用事实记入上述背景，附来源、确认日期、适用版本/范围和时效；推测标为待确认，不据此扩大需求或实现。业务决策及审查发现仍按既有批准边界处理。
- 更新 `PLANS.md`（非 trivial 任务）

### Step 2 — Implement

- 最小改动实现；可选整理不得擅自混入当前改动，范围变化先说明并按已有批准边界处理。
- 保持现有接口与行为契约；修改共享 helper 时，查明受影响的直接及间接调用者，并对照上述入口边界检查参数、分支、校验与副作用。收窄范围或恢复旧行为时，沿入口到 helper 的调用链核验；仅恢复入口函数正文或 diff 相同不足以证明行为已恢复。

### Step 3 — Validate

- 仅运行受影响命令
- 记录关键结果摘要与风险点：将允许改变的行为、必须保持的关键旧行为对应到具体测试名称、核心断言、执行命令及结果，并附相关调用链证据（入口 → helper、关键分支/校验位置）。复用足够的既有测试，仅为证据缺口补关键反例；测试通过总数不能替代行为验证，未覆盖项明确列出。

### Step 4 — Documentation

- 更新断言矩阵（如流程相关）
- 对齐 checklist 与交付说明

## Recommended Kickoff Sequence (Large Repos)

1. Pilot module（默认 `wallet-api`）
2. Iteration 0：质量门禁固定
3. Iteration 1：黄金路径 + 失败不变性
4. Iteration 2：编排回归
5. Iteration 3：沉淀复用夹具
6. Iteration 4：复制到第二模块

## Pre-delivery Independent Review

在实现完成、交付前执行一次独立只读审查；由实现或协调任务负责发起，独立审查任务只报告，不修改文件、不提交，也不自行指挥修复。本流程不增加每个小批次的审批，不替代先 review 后 commit 或已有提交、推送、合并、发布权限。

1. **固定审查范围。** 交给用户 review 前，按行为或方法分组简要说明各处改动的必要性（直接满足需求、必要配套保护或可选整理），不要求逐行报告；可选整理仅在获准范围内纳入。提供原需求、已确认业务边界、相关既有实现、基线/HEAD、固定 diff（含本次暂存、未暂存及新增文件）、可识别的内容摘要，以及验证记录。审查结论绑定这个版本；不得把变化中的工作区当作同一版本。
2. **独立只读审查。** 核对需求偏差、既有能力复用、多余的平行实现或复杂度，以及测试证据是否支持交付结论。同时寻找新功能不正确和非目标旧行为被破坏的反例；按风险检查相关失败路径和未覆盖项，并核对关键不变用例及共享 helper 的直接/间接调用链，不能只看改动函数。区分资金/状态正确性缺陷与可读性、日志问题，分别说明依据和影响。复用 `testing.md`、DoD 和适用的专项 checklist，不重复堆叠规则或穷举全组合。不能独立完成审查时，报告原因与阻塞，不能宣称审查已通过。
3. **先报告、后修正。** 把新发现的具体问题、依据、影响和建议方案先告诉用户；实现任务在取得对应批准后修正，不因审查发现而自动修改。已明确批准且仍在原边界内的修正直接执行，不追溯重问。没有问题也需列出审查版本、范围和未覆盖路径。
4. **最终版本重验与交付。** 修正后运行受影响的验证，并核对最终 diff。若最终版本超出原审查覆盖，补审受影响范围；不能用旧版本的结论代替最终版本。交付列明变更、审查结论、实际验证证据、未覆盖路径及剩余限制；结论对应 Step 3 的具体测试、断言和调用链证据，不以测试总数、上下文多少或 review 轮数保证质量。存在审查阻塞时如实说明，不标为完成。

这是一项由任务执行的交付流程，写入规则不代表已安装 hook、自动化或修改应用设置。
