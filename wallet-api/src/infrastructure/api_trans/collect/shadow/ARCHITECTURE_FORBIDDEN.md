# ShadowAdvancer 架构边界与禁止操作

## 1. 核心架构原则

### 1.1 单一职责原则
- **Advancer**: 唯一的推进器，负责基于当前事实推进归集交易的阶段
- **Scanner**: 负责扫描数据库，发现需要推进的交易并触发 Advancer
- **Worker**: 负责执行具体的任务（如构建交易、广播交易等），只写事实，不负责推进下一阶段
- **Dispatcher**: 负责分发推进意图，确保意图被正确处理
- **Diagnose**: 负责诊断卡住的交易，触发 Advancer 进行重试

### 1.2 推进流程
1. Scanner 扫描数据库，发现需要推进的交易
2. Scanner 调用 Advancer.try_advance()
3. Advancer 检查是否正在运行（带 TTL）
4. Advancer 获取 semaphore 许可（带 timeout）
5. Advancer 查询最新的 DB 状态（带 timeout）
6. Advancer 基于事实状态，按照 ADVANCEMENT_ORDER 顺序检查可推进点
7. Advancer 找到第一个满足条件的推进点，生成对应意图
8. Advancer 非阻塞发送意图给 Dispatcher
9. Dispatcher 处理意图，调用对应的 Worker
10. Worker 执行任务，更新事实
11. Scanner 再次扫描，发现新的事实，重复流程

## 2. 禁止操作

### 2.1 绝对禁止

#### ❌ Worker 直接调用 try_advance
- **原因**: 会破坏推进的单一入口原则，可能导致并发冲突和无限递归
- **正确做法**: Worker 只更新事实，由 Scanner 发现新事实后触发 Advancer

#### ❌ 直接修改 running map
- **原因**: 会破坏并发控制，可能导致死锁或竞态条件
- **正确做法**: 只通过 Advancer 内部的接口修改 running map

#### ❌ 在推进路径中使用 await
- **原因**: 会阻塞推进流程，影响系统吞吐量
- **正确做法**: 所有 I/O 操作都应该在推进路径之外执行

#### ❌ 忽略 semaphore 限制
- **原因**: 会导致数据库压力过大，影响系统稳定性
- **正确做法**: 严格遵守 semaphore 限制，不绕过并发控制

#### ❌ 直接修改数据库状态
- **原因**: 会破坏事实的一致性，可能导致推进逻辑错误
- **正确做法**: 只通过 Repo 层的接口修改数据库状态

### 2.2 强烈不建议

#### ⚠️ 调整 TTL 值
- **原因**: 过小会导致重复推进，过大可能导致长时间阻塞
- **建议值**: 30 秒

#### ⚠️ 修改 semaphore 大小
- **原因**: 过小会限制吞吐量，过大可能导致数据库压力过大
- **建议值**: 通过环境变量 SHADOW_MAX_CONCURRENCY 设置，默认 32

#### ⚠️ 修改推进顺序
- **原因**: 会破坏推进逻辑的一致性，可能导致交易卡住
- **正确做法**: 保持与 scan_round 完全一致

#### ⚠️ 在 diagnose 中执行耗时操作
- **原因**: 会阻塞诊断流程，影响系统的自愈能力
- **正确做法**: 所有耗时操作都应该通过 spawn 执行

## 3. 错误处理

### 3.1 超时错误
- **DB 连接获取超时**: 快速重试
- **DB 查询超时**: 慢速重试
- **Semaphore 获取超时**: 放弃并记录错误
- **Intent 发送失败**: 触发 DiagnoseEvent::IntentDispatchFailed

### 3.2 异常处理
- **Panic**: 由上层捕获，确保系统不会崩溃
- **Cancel**: 正常忽略，不影响系统运行
- **Shutdown**: 优雅退出，确保资源被正确清理

## 4. 性能优化

### 4.1 缓存策略
- **Running map**: 使用 DashMap 进行并发控制，定期 GC 清理过期记录
- **Diagnose 缓存**: 使用 CachedDiagnoser 缓存诊断结果

### 4.2 限速策略
- **Semaphore**: 限制并发 DB 查询数量
- **Revisit 限速**: 同 trade_no 1 秒最多触发一次 revisit
- **GC 限速**: 每 10 秒执行一次 running map GC

### 4.3 非阻塞设计
- **Intent 发送**: 使用 try_send 非阻塞发送意图
- **Diagnose 处理**: 使用 spawn 延迟执行，避免阻塞

## 5. 监控与告警

### 5.1 关键指标
- **推进成功率**: 监控 try_advance 的成功比例
- **超时率**: 监控各种超时错误的比例
- **卡住率**: 监控被诊断为卡住的交易比例
- **并发数**: 监控当前的并发推进数量

### 5.2 日志级别
- **Debug**: 详细的推进过程信息
- **Info**: 正常的推进事件
- **Warn**: 卡住的交易诊断
- **Error**: 严重的错误，需要人工干预

## 6. 部署与配置

### 6.1 环境变量
- **SHADOW_MAX_CONCURRENCY**: 最大并发数，默认 32
- **RUST_LOG**: 日志级别

### 6.2 依赖
- **DashMap**: 并发 map，用于 running 管理
- **Semaphore**: 并发控制
- **Sqlx**: 数据库访问
- **Tokio**: 异步运行时

## 7. 常见问题与排查

### 7.1 交易卡住
- **排查步骤**: 检查 diagnose 日志，查看卡住原因
- **常见原因**: 缺少必要的事实、外部系统错误、超时

### 7.2 推进速度慢
- **排查步骤**: 检查 semaphore 大小、DB 性能、网络延迟
- **常见原因**: semaphore 过小、DB 性能差、外部系统响应慢

### 7.3 系统不稳定
- **排查步骤**: 检查错误日志、CPU 使用率、内存使用率
- **常见原因**: 死锁、内存泄漏、无限递归

## 8. 总结

ShadowAdvancer 是一个交易执行系统级的推进器，不是普通的 async worker。它通过严格的架构设计和并发控制，确保归集交易能够安全、高效地推进。

所有开发者都应该严格遵守本文档中的架构边界和禁止操作，确保系统的稳定性和可靠性。任何违反架构边界的修改都可能导致线上事故，需要经过严格的代码审查。
