# 旧版本归集系统整体说明（事实级）

> ⚠️ 本说明描述的是 **当前代码的真实行为与设计意图**，
> 并不代表推荐的最终架构。
> 任何改动前，请完整理解本文。

---

## 一、系统职责边界

### 旧版本归集系统负责什么？

**负责完整的「归集交易生命周期执行与上报」：**

1. 构建并发送归集交易
2. 跟踪交易广播结果
3. 跟踪链上执行结果（成功 / 失败）
4. 向后端上报交易结果事件（TxRes ACK）
5. 在本地 DB 中记录执行结果与上报状态

### 明确不负责什么？

* ❌ 不负责资产扫描 / 余额计算
* ❌ 不负责链上最终性判定（依赖外部链查询）
* ❌ 不作为全局事实驱动器（非 Scanner 架构）

---

## 二、整体模块划分

旧版本归集由多个 **长期运行的后台 Worker** 组成：

```text
process_collect_tx_send
    └── 负责构建 & 广播归集交易

process_collect_tx_report
    └── 负责上报“交易已发送（TxSend）”

process_collect_tx_confirm_report
    └── 负责上报“交易结果（TxRes）”

shadow
    └── 非主路径兜底触发器
```

它们的共同特点是：

* 都是 **tokio task**
* 都是 **事件 + 定时双驱动**
* 都可以在系统运行期间反复处理同一笔订单

---

## 三、驱动模型（非常重要）

### 旧版本不是 Scanner 模型

旧版本采用的是：

> **Worker 主动执行模型**

具体表现为：

* Worker 自己：

  * 扫 DB
  * 接事件
  * 判断是否重试
  * 决定是否推进状态

而不是：

* 由一个中心 Scanner
* 基于 DB 事实统一决策

---

## 四、触发方式统一模型

所有归集相关 Worker 的 run loop 都遵循同一模式：

```rust
tokio::select! {
    shutdown 信号
    单条 trade_no 事件
    定时 interval 批量扫描
}
```

### 设计目的

* **事件驱动**：降低延迟（单笔立即处理）
* **定时扫描**：兜底（防止事件丢失 / 进程重启）
* **长期运行**：自动恢复能力

### 设计后果（重要事实）

* 同一笔订单 **可能被多次“尝试处理”**
* 系统依赖：

  * 幂等设计
  * DB 字段防重
  * 状态检查

---

## 五、并发模型说明（地址级串行）

### 并发设计原则

> **并发的最小粒度是 from_addr（地址）**

| 维度   | 行为   |
| ---- | ---- |
| 不同地址 | 并行执行 |
| 相同地址 | 严格串行 |

### 实现方式

```rust
DashMap<Address, Weak<Mutex<()>>>
```

* 每个地址对应一个 Mutex
* 使用 `Weak` 防止长期占用内存
* 锁只用于并发控制，不承载业务状态

### 额外限制

* `global_sem` 用于限制整体并发上限（如 64）
* 防止瞬时批量扫描压垮系统

## 六、状态模型（旧版本的真实语义）

### ApiCollectStatus 在旧系统中的角色

这些状态**不是完整状态机**，而是：

> **多个 Worker 之间的“协作标记”**

#### 典型状态含义（按使用行为）

| 状态                   | 含义        |
| -------------------- | --------- |
| Init                 | 待发起归集     |
| SendingTx            | 交易已广播     |
| SendingTxFailed      | 构建 / 广播失败 |
| Success              | 链上成功      |
| Failure              | 链上失败      |
| ConfirmSuccessReport | 成功结果已上报   |
| ConfirmFailureReport | 失败结果已上报   |

⚠️ 注意：

* **不存在一个统一的 Done**
* “完成”是由：

  * 状态 + ack 时间
  * * 后续 Worker 不再扫描
  * 共同形成的隐式终态

---

## 七、ConfirmReport 模块的真实职责

### 它不是“确认交易”

它的职责是：

> **向后端发送“交易结果事件确认（TxRes ACK）”**

### 处理对象

仅处理以下状态：

```rust
ApiCollectStatus::Success
ApiCollectStatus::Failure
```

### 防重机制（DB 级）

```rust
tx_res_ack_sent_at
```

* 一旦写入
* 该订单将永远不再被 ConfirmReport 处理

这是旧版本中**少数完全依赖 DB 事实的防重点**。

---

## 八、重试模型（旧版本特征）

ConfirmReport 的重试基于：

* `updated_at`
* `post_confirm_tx_count`

采用 **线性退避**：

```text
第 N 次失败 → N 秒后再试
```

特点：

* 简单
* 可预测
* 不依赖外部调度器

---

## 九、恢复与幂等假设

旧版本系统 **默认假设**：

1. 同一 trade_no 的操作是幂等的
2. 后端 ACK 接口是幂等的
3. 多次尝试不会造成业务破坏

因此允许：

* 重启后重新扫描
* 同一订单多次进入 Worker
* 由 DB 状态决定“是否继续”

---

## 十、旧版本设计的核心取舍（不是优缺点）

### 它刻意选择了：

* Worker 自治
* 事件 + 定时双保险
* 内存并发控制
* DB 作为结果记录而非调度源

### 它刻意没有选择：

* 中心化 Scanner
* 严格状态机
* DB 事实唯一驱动
* 全局任务调度

---

## 十一、给未来维护者的重要提醒（非常重要）

> ⚠️ **不要在未理解整体模型前，局部修改状态推进逻辑**

特别是：

* ❌ 在 ConfirmReport 中直接改成 Done
* ❌ 引入新的状态但不修改扫描条件
* ❌ 混用 Scanner 与 Worker 推进同一状态

否则极易导致：

* 重复上报
* 状态卡死
* 无法恢复

---

## 十二、迁移前的共识（写给“升级版本”）

> 旧版本不是“写坏了”，
> 而是 **在没有 Scanner 架构前提下的一个完整闭环系统**。

**任何新版本设计，都必须：**

* 明确替代哪些职责
* 明确哪些 Worker 将被废弃
* 明确 Done 的唯一事实来源
